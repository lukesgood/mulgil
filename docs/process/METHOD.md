# 1인 회사 운영 모델 — 역할형 에이전트 개발 방법론

한 사람이 결정하고, 에이전트들이 회사의 역할을 나눠 맡는다. 사람은 **코드를 쓰지
않고 판단한다.** 에이전트는 **판단하지 않고 제안·실행한다.** 둘의 경계가 이 문서의
전부다.

적용 저장소: `lukesgood/sumun`, `lukesgood/mulgil`. 실행 환경: Claude Code
(`.claude/agents/`, `.claude/commands/`), GitHub Issues/PR, git.

## 1. 원칙

1. **에이전트는 제안하고 사람은 결정한다.** 되돌릴 수 없는 일(공개 릴리스, 삭제,
   정책 변경, 외부 발송)은 에이전트가 준비하고 사람이 실행한다.
2. **역할마다 컨텍스트를 분리한다.** 리뷰어는 개발자의 추론을 보지 않는다. 같은
   창에서 짜고 검토하면 검토가 아니다.
3. **모든 것은 git에 있다.** 스펙은 이슈, 결정은 ADR, 상태는 `docs/status/`,
   프로세스는 이 문서. 대화에만 있는 결정은 결정이 아니다.
4. **게이트는 자동, 판단은 수동.** 테스트·누출 회귀·시크릿 스캔은 훅과 CI가 막는다.
   사람은 게이트를 통과한 것만 본다.
5. **비협상 원칙(`CLAUDE.md`)은 모든 에이전트의 상위 지시다.** 어떤 역할도 이를
   넘는 제안을 하지 않는다. 넘어야 한다면 ADR 제안으로 사람에게 올린다.
6. **작게 끝낸다.** 이슈 하나 = 브랜치 하나 = PR 하나 = 하루 안. 넘치면 PM이 쪼갠다.

## 2. 역할

| 역할 | 에이전트 | 맡는 것 | 산출물 | 쓰는 모델 |
|---|---|---|---|---|
| 대표·PO | **사람** | 범위·우선순위·게이트 통과·고객 대화·소유 결정 | 결정 (ADR 승인, 이슈 라벨 `decided`) | — |
| PM | `pm` | 백로그, 스펙(수용 기준 + 요구사항 ID), 주간 계획, 상태 보고, 기획서↔이슈 동기화 | 이슈, `docs/status/YYYY-Www.md` | 최상위 |
| 아키텍트 | `architect` | ADR, 경계 검사(비협상 원칙·물길/수문 경계), `design-needed` 이슈의 설계 | `docs/adr/NNNN-*.md`, 설계 코멘트 | 최상위 |
| 개발자 | `developer` | 이슈 하나를 브랜치에서 구현. 수용 기준 → 테스트 먼저 → 구현 → PR | 브랜치, PR | 상위 |
| 리뷰어 | `reviewer` | 정확성·테스트·가독성. **새 컨텍스트**에서 diff만 본다 | PR 리뷰 코멘트, 승인/반려 | 최상위 (개발자와 다른 세션) |
| 보안 | `security` | auth·RLS·감사·PII·시크릿·의존성 라이선스. 누출 회귀 결과 해석 | PR 보안 코멘트, 위협 메모 | 최상위 |
| QA | `qa` | 수용 기준을 실행 가능한 검증으로. compose E2E, 회귀 스위트 | 테스트 결과, `gate:done` 판정 | 상위 |
| 릴리스 | `release` | 버전·체인지로그·태그·차트 버전·이미지 서명 준비 | 릴리스 PR, 태그 **초안** | 하위 |
| 문서 | `docs` | README·가이드·ADR 인덱스를 코드와 맞춤 | 문서 PR | 하위 |
| 고객 대역 | `persona` | CISO·에이전트 개발자·현업의 눈으로 스펙 비판. **인터뷰 대체 아님** | 스펙 코멘트 | 상위 |

모델 등급은 비용 통제용이다. 판단이 무거운 역할(PM·아키텍트·리뷰어·보안)에
최상위, 기계적 역할(릴리스·문서)에 하위.

## 3. 이슈 하나의 흐름

```
사람: 우선순위 결정
  │
  ▼
pm ── 스펙 작성 ──▶ 이슈 (문제 · 수용 기준 · 요구사항 ID · 리스크)      [gate:ready]
  │                       │ design-needed 라벨이면
  │                       ▼
  │                  architect ── 설계 코멘트 또는 ADR 초안 ──▶ 사람 승인
  ▼
developer ── 브랜치 · 테스트 먼저 · 구현 ──▶ PR (스펙 링크, 체크리스트)
  │
  ├──▶ reviewer  (새 세션, diff만)  ──▶ 승인 / 반려
  └──▶ security  (새 세션, 영역 해당 시) ──▶ 승인 / 반려          ← 둘은 병렬
  │
  ▼
qa ── 수용 기준 실행 · 회귀 스위트 ──▶ gate:done 판정
  │
  ▼
사람: 머지 (저위험 + 전부 초록이면 PM이 머지 제안, 사람이 클릭)
  │
  ▼  (주 1회)
release ── 체인지로그 · 버전 · 태그 초안 ──▶ 사람이 태그 푸시
docs ── 문서 동기화 PR
```

병렬 원칙: 리뷰어와 보안은 서로의 코멘트를 보지 않고 쓴다. 충돌하면 아키텍트가
조정안을 내고 사람이 정한다.

## 4. 게이트

### Definition of Ready (`gate:ready`) — PM이 붙인다
- [ ] 문제가 한 문장으로 적혀 있다
- [ ] 수용 기준이 실행 가능한 문장이다 ("…하면 403을 받는다")
- [ ] 요구사항 ID(G1, T2 …) 또는 ADR 번호가 연결돼 있다
- [ ] 하루 안에 끝나는 크기다. 아니면 쪼갰다
- [ ] 경계(물길/수문, 비협상 원칙)를 건드리면 `design-needed`
- [ ] **범위 안이다.** 기획서 §5와 현 Phase 범위에 없는 기능은 ADR 없이는
  `gate:ready`가 되지 않는다. "하지 않는 것" 목록(mulgil ADR 0004·0005,
  sumun ADR 0002·0003)에 있는 항목은 ADR을 바꾸는 PR이 먼저다

### Definition of Done (`gate:done`) — QA가 붙인다
- [ ] 수용 기준마다 테스트가 있고 초록
- [ ] 누출 회귀 스위트 초록 (ACL·마스킹 누출 0건)
- [ ] 리뷰어 승인 + (해당 시) 보안 승인
- [ ] 경계를 바꿨으면 ADR이 머지됐다
- [ ] 사용자에게 보이는 변화면 docs 이슈가 열렸다

### 자동 게이트 (훅·CI) — 사람이 보기 전에 막는다
- pre-commit: 포맷, 린트, 시크릿 스캔
- CI: 단위 테스트, 누출 회귀, 라이선스 검사, `dbt parse`(물길)
- PR 템플릿의 체크리스트가 비어 있으면 리뷰어가 반려

## 5. 주간 리듬 (1인 스프린트)

| 요일 | 역할 | 일 |
|---|---|---|
| 월 | pm → 사람 | `/plan-week`: 지난주 결과 + 이번 주 이슈 ≤5개 제안. 사람이 순서 확정 |
| 화–목 | developer / reviewer / security / qa | 이슈 단위 흐름 (3장) |
| 금 | qa → release → docs → pm | 회귀 전체 실행, 릴리스 초안, 문서 동기화, `docs/status/YYYY-Www.md` 상태 보고 |
| 금 | 사람 | 상태 보고 읽고 다음 주 우선순위 메모. 디자인 파트너에게 보낼 한 줄 |

상태 보고 형식 — **첫 줄은 계획 대비 완료율(%)과 이번 주 추가된 범위(건)**,
그 아래 한 일 / 안 된 일과 이유 / 다음 주 / 결정 필요 사항. 완료율이 3주
연속 60% 미만이면 PM은 Phase 2b를 Phase 3로 미는 로드맵 수정 PR을 올린다
(mulgil ADR 0005). 이 보고가 기획서 로드맵과 어긋나면 PM이 로드맵 수정
PR을 함께 올린다.

## 6. 사람이 결정하는 것 — 이 목록 밖은 에이전트가 진행한다

1. 이슈 우선순위와 주간 범위
2. ADR 승인 (경계·비협상 원칙·프로필 추가·의존성 추가)
3. `design-needed` 설계 선택지 중 하나
4. PR 머지 (저위험은 클릭만, 고위험은 읽고)
5. 릴리스 태그 푸시, 공개/비공개 전환
6. 정책·예산·삭제 같은 되돌릴 수 없는 운영 행위
7. 고객·파트너와의 대화 (persona는 대역이지 대체가 아니다)
8. 소유·라이선스·가격

## 7. 컨텍스트 분리 규칙

- 각 역할은 `.claude/agents/<role>.md`의 시스템 프롬프트로 시작한다. 공통 상위
  지시는 `CLAUDE.md`.
- 리뷰어·보안·QA는 **개발 세션과 다른 세션**에서 실행한다 (`/review`가 서브에이전트로
  띄운다). 같은 세션에서 "이제 리뷰해줘"는 금지.
- 에이전트는 다른 에이전트의 추론을 읽지 않고 **산출물**(이슈·PR·ADR·테스트 결과)만
  읽는다. 산출물이 git에 있는 이유다.
- 역할을 바꿔야 하면 세션을 바꾼다. 한 세션에서 두 역할은 한 역할이다.

## 8. 비용 통제

- 역할별 모델 등급(2장). 기계적 역할은 낮은 등급.
- 리뷰어·보안은 diff만 받는다. 저장소 전체를 다시 읽지 않는다.
- 주간 상태 보고에 토큰 비용 한 줄. 치수(ops)의 호출자별 비용 귀속과 같은 생각 —
  개발 과정의 비용도 역할별로 본다.

## 10. 이 방법론의 한계

- persona 에이전트는 고객이 아니다. 인터뷰 0건인 상태를 숨기지 않는다.
- 리뷰어가 개발자와 같은 모델이면 같은 맹점을 공유한다. 가능하면 다른 모델 또는
  다른 프롬프트 스타일.
- 1인 체제에서 가장 자주 깨지는 건 "사람의 결정 시간"이다. 금요일 30분을
  지키지 못하면 에이전트들이 멈춘다 — 그게 정상이다. 멈추지 않고 스스로 결정하는
  에이전트가 비정상이다.
